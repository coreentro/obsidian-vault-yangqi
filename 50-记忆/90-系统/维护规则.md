# 🔧 维护规则（Agent 契约）

> 这是 **AI 每次任务的操作规程**。用户不需要手动维护本层。

## 🔁 每次任务的两个动作

### ① 任务开始前：先检索，再动手

```text
1. 读 50-记忆/00-记忆索引.md  → 定位相关项目卡
2. 读 该项目卡（尤其「当前进度」「失败方案」「踩坑」）
3. 全层关键词检索：在 50-记忆/ 内 grep 任务关键词
4. 若涉及知识正文 → 顺链接进 20-领域 / 30-资源
5. 缺上下文才问用户；已在记忆里的绝不重复问
```

命令模板（把 `<KW>` 换成关键词）：

```bash
V="$HOME/Library/Mobile Documents/iCloud~md~obsidian/Documents/yangqi"
grep -ril "<KW>" "$V/50-记忆" --include="*.md"
```

### ② 任务结束后：只沉淀"未来还有用"的

| 产出 | 写到哪 |
|---|---|
| 做完了什么 | 项目卡「已完成」（带日期）|
| 现在到哪一步、下次从哪接 | 项目卡「当前进度」（**覆盖，不堆积**）|
| 有替代方案的选择 | [[50-记忆/02-决策记录]]（追加到最上面）+ 项目卡「关键决策」摘一行 |
| 试过但不行的 | 项目卡「失败方案」+ 通用的进 [[50-记忆/03-踩坑与失败方案]] |
| 现象→真因→正确做法 | [[50-记忆/03-踩坑与失败方案]] |
| 验证可跑的配置/命令 | [[50-记忆/04-技术方案库]] |
| 路径、端口、账号体系 | [[50-记忆/05-环境地图]] |
| 新的偏好或红线 | [[50-记忆/01-长期偏好]] + 决策记录留痕 |
| 下一步计划 | 项目卡「下一步」（**覆盖式**，最多 5 条）|
| 代码/配置变更 | 项目卡「已完成」写：改了哪个文件 + 改了什么 + 为什么 |

同时更新 frontmatter 的 `updated` 与 `status`，必要时同步索引项目总表的状态图标。

## ✅ 该写 / ❌ 不该写

| ✅ 写 | ❌ 不写 |
|---|---|
| 结论、判断、真因 | 逐字对话记录 |
| 有替代方案的决策 + 理由 | 显然的常识 |
| 失败方案与踩坑 | 一次性临时状态（今天开了几个窗口）|
| 已验证的命令 / 配置形状 | **密码、API Key、Token、Cookie** |
| 稳定路径、端口、账号体系 | 一周后就过期的东西 |
| 下一步计划 | 重复已有内容（改为加链接）|

判断标准一句话：**一周后还有用吗？** 没用就不写。

## 🧾 项目卡九段式

新项目复制 [[50-记忆/90-系统/项目卡模板]]，小节标题**不要改名、不要删**（空的写「暂无」）：

```text
📋 项目背景 / 🎯 长期偏好与约束 / 🧩 关键决策 / ✅ 已完成
📍 当前进度 / ❌ 失败方案 / 🕳️ 踩坑 / 🧪 技术方案 / ⏭️ 下一步
```

`覆盖式` = 当前进度、下一步（只留最新）
`追加式` = 已完成、关键决策、失败方案、踩坑（保留历史，带日期）

## 🧹 防膨胀

- 项目卡正文尽量 **≤200 行**；超了把细节挪到 `20-领域` 正文，卡里只留链接。
- 「已完成」超过 20 条 → 早期条目合并成一行阶段总结。
- 项目结束 → `status: 已完成`，索引里改 ✅；**不删卡**（用户红线：不主动删）。
- 每条踩坑只在一处写全，别处用链接引用。

## 🔒 安全

写入前自检：是否含 `sk-`、`Bearer`、`api_key=`、`token=`、密码、cookie？
有 → 只写「变量名 + 所在文件」，值留在 `~/.hermes/.env`。
